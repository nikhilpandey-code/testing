MY UNDERSTANDING OF LAYA
=========================
(Re-checked against the source code on 2026-11-18. Corrections from the first version are
listed at the end.)

Short version
-------------
Laya is a small, local, on-device "System 1" decision engine. You give it a piece of
text (or a JSON document, or a list of conversation turns) plus a set of typed questions,
and it answers all of them with one neural-network forward pass, with no text generation.
It is multilingual (100+ languages through its multilingual checkpoint) and it returns a
probability for every option, not just a label.

It is published as the Python package `laya` (version 0.3.20, Apache-2.0, by Convai
Innovations, "Development Status :: 4 - Beta"), with a TypeScript port called `laya-ts`
(version 0.1.0) in the same repository.

The project describes itself honestly as "a fast base to specialise, not a zero-shot
decision engine": the base checkpoints are close to chance on structured business decisions
until you fine-tune them on your own labelled data.


What problem it solves
----------------------
Many apps need to make quick, structured decisions about incoming text:
  - Which department should handle this ticket?           (billing / technical / other)
  - How urgent is this?                                    (not urgent / soon / critical)
  - Does this user threaten to cancel?                     (yes / no, with a probability)
  - Is this prompt a jailbreak or injection attempt?       (guardrails)

Doing this with an LLM that generates text is slower, costs money per call, and gives
output that has to be parsed. Laya instead reads the input once and scores the answer
options directly. The README quotes 32.8 ms for one question on a T4 GPU with the
multilingual checkpoint (39.5 ms with the English one), and 7.2 ms per question batched.
On CPU it is much slower (the README says roughly 193 to 464 ms per request preloaded).


The three question types
------------------------
Every question has `instructions` (the question text) and a `type`:
  - choice : pick one option. `criteria` is a dict of label -> description, or a plain
             list of labels.
  - score  : pick a level on an ordered scale. `criteria` is a list, level 0 first.
  - noul   : a yes/no question. Returns P(yes) from 0.0 to 1.0. `criteria` is optional and
             may only use the keys "true" and "false". An optional `labels` mapping changes
             only the wording the model sees.

Every answer contains the probabilities, a `confidence` field, an `answer_confidence` field
and an `action.act_probability` field. Only `answer_confidence` (the top probability) is the
calibrated number; see "how laya works.txt".


The three checkpoints and the Router
------------------------------------
All three live in one Hugging Face repo, convaiinnovations/laya (only the requested
subfolder is downloaded). They also exist as standalone repos.
  - english          ModernBERT-large, 421M params, 512-token context. Best for English.
  - multilingual     mmBERT-base, 322M params, 1024 tokens (up to 8192 with max_len=8192).
                     100+ languages, and about 2x faster.
  - typed-decisions  ModernBERT-large, 421M params, 1024 tokens, fine-tuned on four
                     synthetic workflows (agent trace observability, customer service,
                     invoice processing, security incidents). Never picked automatically
                     unless you opt in.

The `Router` is the recommended entry point. It decides which checkpoint to run with a
small dependency-free detector (lang.py): first the Unicode script (non-Latin text goes to
multilingual), then for Latin text a function-word and accented-letter heuristic that holds
word lists for 10 languages (en, fr, de, es, pt, it, nl, ro, bn, az). The key observation
in the docs is that the English checkpoint collapses on non-English text while staying
confident (Khmer: 0.000 accuracy at 0.952 confidence), so it must not see that text.

The Router keeps up to two checkpoints loaded by default (max_loaded=2, least recently used
is evicted), can preload all of them (Router(preload=True)), routes and batches whole
workloads (predict_batch, route_batch), and has route() to show the decision without loading
any model. Accepted name aliases include "en", "ml", "multi", "typed".


How it works inside (summary; details in "how laya works.txt")
--------------------------------------------------------------
  1. Input: a state and a dict of questions.
  2. Each question becomes one token sequence:
       [CLS] <type> question: <instructions> [SEP] [MASK] opt0 [MASK] opt1 ... [SEP] state [SEP]
     The state is tokenised once and shared by every question.
  3. A bidirectional encoder (ModernBERT-large or mmBERT-base) reads the whole sequence.
  4. A decision head (a small transformer, 2 layers by default, plus a question-type
     embedding) scores the output at each [MASK] position: one logit per option.
  5. Logits are divided by a fitted temperature (per question type and option-count bucket,
     clamped to 0.5..5.0) and turned into probabilities with softmax.
  6. Training: "RLCD", described in the README as reinforcement learning with a GRPO-style
     policy gradient and rewards that are strictly proper scoring rules (log score,
     spherical score, and ranked probability score for ordinal questions). Such rewards
     push the model to report honest probabilities.

Practical extras built on top:
  - Long documents: the multilingual checkpoint accepts max_len=8192.
  - Large option lists: shortlist.py picks the top k options with an embedding function
    before the real prediction.
  - Email cleaning (email.py): strips quoted replies, sign-offs and disclaimers in English,
    Portuguese and Spanish, and caps the body at 3,000 characters.
  - Schema-driven decisions (structured.py): a JSON Schema or pydantic model becomes the
    questions; typed values come back.
  - Presets (presets.py): triage, email, guard, moderation, router question sets.


Where it can be used
--------------------
  - Python, in process:          `from laya import Router` (also `Agent`, `load`, `decide`).
                                 `Agent.predict` is the same method as `Agent.system_one`.
                                 `RLAgent` is only an alias for `Agent`.
  - Command line:                `laya "text"` (routing only), `--predict`, `--preset triage`
  - HTTP server:                 `laya-serve`: POST /v1/systemone (TypeSafe Jev's wire
                                 format), GET /health, optional bearer key. Runs one
                                 prediction at a time.
  - MCP server:                  `laya-mcp-server` with tools laya_status, laya_route,
                                 laya_predict, laya_preset.
  - LangChain / LangGraph:       LayaRouter, LayaGuardrail (+ LayaGuardrailError), LayaTriage,
                                 LayaEvaluator; in process or against a remote laya-serve.
  - Fast GPU path:               laya/fast.py with TileLang kernels (tl_kernels.py), bf16 and
                                 CUDA graphs; extra `laya[fast]`.
  - ONNX runtime:                laya/onnx_agent.py (ONNXAgent); extra `laya[onnx]`.
  - TypeScript:                  laya-ts runs on Node (CPU/CUDA) and in the browser (WebGPU
                                 with WASM fallback) from a split ONNX export (encoder.onnx +
                                 head.onnx). ESM-only.
  - Devices:                     auto-detects CUDA, then Apple MPS, then Intel XPU, then CPU.
                                 Falls back to CPU if the GPU runs out of memory.
  - Docker and Nix:              Dockerfile, compose files (CPU, CUDA, DGX Spark, HTTP), a Nix
                                 flake with a NixOS service module.
  - Notebook:                    fine-tuning on Kaggle's free 2x T4 GPUs (about 4 to 5 hours
                                 for 4 epochs over ~30k questions).


Extensibility: hooks
--------------------
hooks.py lets you observe or change every prediction without forking Laya. Events:
on_predict_start, on_predict_end, on_route, on_load, on_evict, on_error. A start hook can
rewrite the states and questions, change the token budget for that call, or skip inference
with a cached result. An end hook can rewrite the result. examples/hooks/ has audit logging,
caching, PII redaction and OpenTelemetry tracing samples.


Repository layout (what is where)
---------------------------------
  laya/                  the Python package: about 5,000 lines in the core modules plus about
                         1,200 in mcp/ and integrations/ (about 6,250 lines in total)
    agent.py             Agent: loads one checkpoint, runs predict/system_one, predict_batch,
                         decide; load() helper

    structured.py        JSON Schema / pydantic -> questions and typed values

Rules the project sets for itself (from AGENTS.md and CONTRIBUTING.md)
-----------------------------------------------------------------------
  - Laya must run locally. No dependency on a hosted service or external API in the core.
  - Do not change the public API without updating tests/test_hooks_api.py, which is the
    API contract.
  - Before a change is done, run:
        ruff check laya/ --select=E9,F63,F7,F82,F401,F811 --line-length=120
        python -m compileall -q laya/ tests/
  - Do not reformat files or reorder imports. Match the style of the file you edit.
  - Commit messages use conventional prefixes such as feat(agent):, fix(router):,
    perf(common):, docs(hooks):, test(batch):. One logical change per commit.
  - Pull requests are written in English, rebased on main, and report before/after numbers
    when a change moves accuracy, latency or memory.
